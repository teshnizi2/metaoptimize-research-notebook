**The rule reproduces exactly and is CONFIRMED AND STRENGTHENED.** n = 356 same-config,

**Two things the original got right for a fuzzier reason than it needed.** A two-way orthogonal
ANOVA (batch × seed) on the 42 config cells carrying a complete sub-grid gives
**BATCH F(62,85) = 5.47, p = 6.9e-13, sd_batch ≈ 0.21 pp** and **SEED F(60,85) = 1.21, p = 0.213,
sd_seed ≈ 0.04 pp**. So it is not loosely that "seed carries no reproducibility": **seed is
statistically NULL and batch is a large random effect.** A one-way ANOVA on family across 51
cells / 380 runs independently gives F(81,248) = 4.19, p = 2.6e-18, robust to conditioning on
Slurm account (account itself is null, F = 1.19).

### 2.2 Four corrections to the audit itself

1. **"Across-seed sd 0.1590" is mislabelled.** It is the sd over *all runs* in a cell, so it
   contains the same-seed replicate spread it is being compared against — the comparison is
   partly circular. The genuine across-seed statistic (sd of **seed means**) is **0.1516** over
   154 configs; restricted to one run per seed it is **0.1562** over 100 configs.
   `CORRECTIONS.md:6218` says "156 configs", the audit says 160, the recomputation gives
   154/160/100 depending on definition — **the reproduction is close, not exact.** The verdict
   is unchanged: 0.1793 vs 0.1516–0.1562 is still "the same number".
2. **The floor is not a constant.** "√2·sd_batch ≈ 0.20 pp, which does not shrink with n" is
   right only for one-batch-vs-one-batch. With k distinct batches per arm in balanced
   composition it averages down as **√(2/k_eff)·sd_batch**, and with **matched composition it
   cancels outright**. The audit's own br6+bl5 reading (se 0.111, two batches in *both* arms, no
   floor added) and its four-deep D pool both rely on exactly that. The amended standard says so.
3. **"Batch" is not exchangeable noise, and hardware is not the cause.** The corpus spans three
   GPU classes (L4 517, 2080 Ti 191, A100 89) over 23 nodes, and in 18 of the 42 ANOVA cells
   batch is perfectly confounded with GPU class. Measured *within* (config × batch family):
   2080Ti−L4 **+0.035** (n=45), A100−L4 **−0.021** (n=21), A100−2080Ti **+0.112** (n=5) — **no
   systematic hardware offset.** With hardware excluded, the ~0.21 pp effect is attributable to
   tree/code/config state at submission — a *diagnosable bias*, not exchangeable variance. **The
   right instrument is therefore a POOLING GATE on the hz9 H0.5 pattern, not a blanket variance
   inflation.** Two of the paper's own D readings have imbalanced GPU composition between arms
   (mm1: chunk 1×L4 + 2×A100 vs node 3×A100; ar1-D: chunk 1×2080Ti + 2×L4 vs node 2×2080Ti +
   1×L4) and neither the audit nor FINDINGS reports it. GPU-class composition should join box
   occupancy in the per-batch disclosure line.
4. **A k/k per-seed gate is a sign test everywhere, including within a batch.** Pairing removes
   ~8% of variance (sd_seed 0.044 vs sd_resid 0.152), and seed is null at p=0.213 — that
   calculation is not conditional on batch. Within-batch gates are not invalidated, but they are
   **weaker than their wording implies** and their power must be quoted as a binomial sign test.
   Registered in `analysis/c83_gen_score.py` and in `analysis/c72_hz9_score.py`'s corrected
   docstring.

### 2.3 Do NOT over-apply this rule

- **Within-batch pairing is completely untouched.** The whole tail prescription, every c58 cell,
  hz9's H1/H1b and CORRECTIONS 113's D_w need no change whatsoever.
- **Pooling already-differenced within-batch contrasts across batches is fine.** This is the trap
  the original flag fell into. Check whether the offset cancels *inside each summand* before
  flagging anything.
- **The point estimate never moves in a balanced design.** Not one point estimate changed under
  re-scoring — only se, t and df. A claim several times above the ~0.20 pp floor does not become
  false because it was mislabelled "paired".

carries 1.8× more coordinates, so the scorer reports **rec_hi per seed per arm as a first-class
number** and voids any contrast whose arms differ by >0.10 in occupancy.

### Batch 2 — `gc1`, the CIFAR-100 screen. 8 jobs, ~9 GPU-h.

`bin/c83_gen_c100_screen.sh` + `analysis/c83_gc1_score.py` (**110/110 selftest PASS**).
`nodewise` (m=14,600) vs `chunk771` (14,595, −5), ResNet18_c100/CIFAR-100, 4 seeds, ms=**1e-4**.

**Three things changed at closeout and all three were defects.**
1. **ms moved 1e-3 → 1e-4.** At 1e-3 the reachable β interval strictly *contains* the box
   (ceiling from epoch 9.3), so ~90% of training would run clamped — and `fa1` established that
   this box class **changes the optimiser**, not merely the instrument. A clamped-regime D is a
   **different estimand** from the box-free anchors the screen exists to compare against.
   Guard 1h was **inverted** accordingly: it now refuses a reachable *floor* and discloses the
   ceiling. Cost: the S2 cross-batch offset diagnostic is **withdrawn** (it required a shared ms,
   was cross-batch *and* cross-account, and carried the 0.20–0.29 pp floor).
2. **The planning sd moved 0.419 → 0.226.** The old figure pooled five granularities and was
   **78% layerwise by weight** — an arm gc1 does not run. Pooled over the **fine** arms only
   (nodewise sd 0.084 n=3, weightwise 0.309 n=3) it is 0.226 on 4 df, so se(D) at n=4 is
   **0.160** and a CIFAR-10-sized D = +0.5 lands at **t = 3.1**. The screen *is* powered for the
   campaign's own point prior.
3. **The stopping rule was rewritten.** The registered rule — "|D| ≥ 1.0 pp → proceed, else close
   as unaffordable" — classified the campaign's own pooled prior (+0.5805) as a **negative**: its
   modal outcome was a false close. Worse, the 1.0 pp threshold came from a "14× amplification"
   prior computed as layerwise 69.594 − scalar 22.560, where the scalar arm reads **22.6% on a
   100-class task** — a failed arm, not an amplified granularity effect, and silent about a
   count-matched contrast between two fine partitions both sitting near 71%. The replacement
   resolves on the **realised** statistic: **REGIME FAILURE** (either arm's sd > 1.0 pp, or a
   collapsed/truncated seed) → CLOSE-UNRESOLVED; |t| ≥ 3 → CLOSE-CONFIRMED; unresolved with
   realised se ≤ 0.30 → PROCEED; realised se > 0.30 → CLOSE-UNAFFORDABLE. **A small point
   estimate can no longer close this question.** The regime abort exists because no CIFAR-100 run
   exists at ms=1e-4 at all, so the *level* both arms land at is unpredicted.

**Forbidden in every branch, registered before any data:** "the tail prescription does not
generalise to CIFAR-100". At se 0.160 that sentence needs a powered n=15 cell (30 jobs, ~20
GPU-h), which is the only pre-authorised expansion.

## 4. THE SINGLE MOST IMPORTANT THING THE CLOSEOUT REVEALED

**The campaign has been measuring the mechanism at half the resolution it thought, and the fix
was free.**

Rule 14's real content is not "seeds don't pair". It is that **BATCH is a large random effect
(F(62,85) = 5.47, p = 6.9e-13, sd_batch ≈ 0.21 pp) while SEED is statistically null (p = 0.213)**
— and hardware is *not* the cause (2080Ti−L4 +0.035, A100−L4 −0.021, measured within cell ×
family), which leaves tree/code state at submission. That single fact reaches straight into the
experimental design of everything that has not yet run:

The paper's load-bearing sentence is **"D is large AND G is null"**, so the number that carries
it is **D − G**. On ResNet18 that number was measured **inside one batch** (cc1: four arms, one
ms, one box) and reads **+0.716 at t 2.9**. The ResNet34 replication had been designed as **two**
batches at **two** stepsizes — which inserts 2·sd_batch² into exactly that contrast, giving
se ≈ 0.33 pp, so a true +0.5 would have landed at **t = 1.5**. The replication would have had
**roughly half the statistical power of the result it was replicating, for the identical 36
jobs.** Merging the two into one cc1-shaped batch costs nothing, cancels the batch offset by
construction, and lifts D − G to **se 0.116**.

**A batch is not a scheduling unit. It is the unit of measurement.** Every contrast that matters
belongs inside one. The corpus already had the right instrument — hz9's H0.5 pooling gate, which
can only VOID — and it was used once.
