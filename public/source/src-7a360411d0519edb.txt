r"""PATCH_CHUNKVEC -- a PER-TENSOR chunk-size VECTOR, so the singleton count can be
varied independently of the ndim>=2 partition.  Written for `bin/c84_singleton_ladder.sh`
(`sl1`), which was KILLED PRE-DATA and DELETED at cycle-84 review -- SEE THE OPERATOR NOTE
BELOW BEFORE APPLYING THIS TO ANYTHING.

WHY THIS PATCH HAS TO EXIST AT ALL
----------------------------------
The campaign's tail result is that the whole matched-count partition gap lives in the
degenerate size-1 groups:

    D = chunk777 - nodewise      (m 14,421 vs 14,420)   +0.485 / +0.581 / +0.697 / +0.727
    G = chunk2325 - nodewise1d   (m = 4,851 EXACT)      +0.295 (UND) / +0.011 / -0.001

Two endpoints are not a dose-response.  The obvious ladder -- keep k of ResNet18's 41
one-dimensional tensors per-channel and collapse the other 41-k -- is DEAD ON ARRIVAL,
and the reason is arithmetic rather than statistical: with the ndim>=2 side left at
nodewise, m(k) = 4,851 + S_k - k, so m - S_k is trapped in [4,810, 4,851] and
corr(S, m) = 0.9999991 over all 42 rungs.  That ladder measures COUNT, not singletons.
It is the defect that got `sf1` withdrawn (docs/CORRECTIONS.md 111.2, defect 3).

THE FIXED-m LADDER, WHICH IS WHAT THIS PATCH MAKES EXPRESSIBLE
--------------------------------------------------------------
Hold m at ~14,420 by chunking the ndim>=2 tensors at a PER-RUNG K2 while injecting
singletons on the one-D side:

    rung Lk = { contiguous chunks of K2 weights on every ndim>=2 tensor }
            + { per-channel (size-1) groups on k of the 41 one-D tensors }
            + { ONE group on each of the remaining 41-k }

    m(k, K2) = G2(K2) + S_k + (41 - k),   G2(K2) = sum_{ndim>=2} ceil(numel / K2)

Recomputed from the built ResNet18's real shape list (62 tensors, 11,173,962 weights,
41 one-D tensors holding 9,610 scalars, 21 ndim>=2 tensors giving 4,810 nodewise groups),
with K2 the argmin of |m - 14,420| over K2 in [512, 4000]:

    L0  k= 0  K2= 777  G2=14,380  m=14,421 (+1)  S=    0  f=0.00000
    L1  k= 7  K2= 802  G2=13,927  m=14,409 (-11) S=  448  f=0.03109
    L2  k=14  K2= 844  G2=13,237  m=14,416 (-4)  S=1,152  f=0.07991
    L3  k=21  K2= 914  G2=12,226  m=14,422 (+2)  S=2,176  f=0.15088
    L4  k=28  K2=1070  G2=10,442  m=14,423 (+3)  S=3,968  f=0.27512
    L5  k=34  K2=1417  G2= 7,893  m=14,428 (+8)  S=6,528  f=0.45245
    L6  k=41  K2=2325  G2= 4,810  m=14,420 (+0)  S=9,610  f=0.66644
    C3  deep subset (4 x 512 + 2 x 64 = 2,176 singletons at k=6), K2=915,
        G2=12,213, m=14,424 (+4), f=0.15086 -- the ORDERING CONTROL for L3.

m varies by 19 groups = 0.13% while the singleton fraction f = S/m sweeps 0 -> 0.666.

WHY PATCH_CHUNKWISE CANNOT DO THIS, CHECKED AGAINST THE LIVE FILE RATHER THAN ASSUMED
--------------------------------------------------------------------------------------
`chunkwise` stores ONE GLOBAL INTEGER (`self.chunk_size = int(_cm.group(1))`) and applies
it uniformly to all 62 tensors in all three of its branches (init, beta_to_alpha,
block_product).  There is no per-tensor granularity construct anywhere in HF.py --
nodewise, nodewise1d, permnode and chunkwise are each all-or-nothing over the whole net.
"chunk the ndim>=2 tensors at K2 while giving k of the one-D tensors per-channel
treatment" is therefore NOT EXPRESSIBLE.  `grep -i nodewisep` over the live cluster file
returns nothing; CORRECTIONS 111.2 records the same blocker.

WHAT THIS PATCH ADDS
--------------------
`--stepsize-groups chunkvec<ND><MODE><ARG>`, matched by `^chunkvec(\d+|n|w)(s|r|x)([0-9.]*)$`:

    <ND>    the chunk size applied to every tensor with ndim >= 2:
              <digits>  that literal K2
              n         numel // shape[0], i.e. NODEWISE on that tensor
              w         1, i.e. WEIGHTWISE on that tensor
    <MODE>  which of the one-D tensors get size-1 (per-channel) groups; the rest get
            exactly ONE group each (chunk size = numel):
              s<k>      SHALLOW-FIRST: the first k one-D tensors in named_parameters order
              r<k>      REVERSE-DEPTH: the last k one-D tensors in that order
              x<i.j.k>  an EXPLICIT dot-separated list of 0-based ranks into the one-D
                        tensor list (empty list allowed, and equals s0)

The ladder's eight arms are then `chunkvec777s0`, `chunkvec802s7`, `chunkvec844s14`,
`chunkvec914s21`, `chunkvec1070s28`, `chunkvec1417s34`, `chunkvec2325s41` and the
ordering control `chunkvec915x36.37.38.39.8.9`.

WHY THIS IS THE LOW-RISK SHAPE OF THE CHANGE
--------------------------------------------
A per-tensor chunk vector SUBSUMES FOUR EXISTING CODE PATHS, so the test suite asserts
BITWISE EQUIVALENCE AGAINST UNPATCHED BEHAVIOUR rather than against my expectation:

    chunkvecns41   ==  nodewise      EXACTLY   (ndim>=2 at numel//shape[0]; all 41
                                                one-D tensors at chunk size 1, which
                                                for a 1-D tensor IS per-channel)
    chunkvecns0    ==  nodewise1d    EXACTLY   (the same, with every one-D tensor
                                                collapsed to a single group)
    chunkvec777s0  ==  chunk777      EXACTLY   (every one-D numel <= 512 < 777, so
                                                chunk777 already gives those tensors
                                                one group each -- this is why ladder
                                                rung L0 IS an already-run arm and
                                                doubles as the instrument check)
    chunkvecws41   ==  weightwise    EXACTLY   (every tensor at chunk size 1)

Those are the boundaries the task names -- k=41 must be plain nodewise, k=0 must be
nodewise1d -- and they are asserted numerically in `tests/test_chunkvec.py`, on CPU,
against the UNPATCHED code paths.  They are exact, not approximate: `Lion_meta_update`
is `beta <- (1-ms*wd)*beta - ms*sign(.)` applied elementwise with no norm and no
cross-element reduction, so holding beta in a different list shape cannot change an
update, and for a row-major tensor of shape (d0, d1, ...) group g of the nodewise
partition IS the flat slice [g*gs, (g+1)*gs) -- the identity PATCH_NODEBN's own suite
already established and tested.

INERTNESS
---------
Four additions, three of them guarded by `self.stepsize_type == 'chunkvec'`, a type
reachable only when `--stepsize-groups` matches the chunkvec regex.  `^chunk(\d+)$`
cannot match a chunkvec string (the character after `chunk` is `v`, not a digit) and the
chunkvec regex cannot match a chunk string, so the two dispatches are disjoint by
construction; the chunkvec test is placed FIRST anyway so the disjointness is not
load-bearing.  Every prior batch used a granularity string that fails the chunkvec
regex, so no existing configuration can enter any new branch and every earlier run stays
reproducible.  'chunkvec' is a substring of neither 'scalar' nor 'blockwise', which
matters because HF.py really does contain two REVERSED substring dispatches
(`self.stepsize_type in 'scalar'`, `... in 'blockwise'`); that is asserted below rather
than trusted.  Every other dispatch is `in (...)` on a TUPLE or an exact `==`.

THE PROBE COMES FOR FREE, AND THAT IS CHECKED, NOT ASSUMED.  `_probe` branches on
`stepsize_type in ('scalar','layerwise','blockwise')` -> beta is a single tensor, else ->
beta is a per-layer LIST.  'chunkvec' takes the LIST branch, the same one nodewise,
nodewise1d, permnode and chunkwise take, so `n_beta`, `beta_true_min/max`, `n_at_lo/hi`,
`frac_neg` and the PROBE5 sign counter all read the chunkvec partition unchanged.

MEMORY.  Nothing per-weight is stored: three small python lists of per-tensor ints
(cvec_K, cvec_counts, cvec_numel) plus the shape list.  Unlike PATCH_PERMNODE this adds
no index tensors and no resident memory.
